    H7_BSP 平台架构

    文档摘要

    本文档定义基于 STM32H723VGT6 的 H7_BSP 通用电控平台顶层架构。核心议题：RTOS 环境下的时间精度保障、中断优先级分层策略、以及在实时控制系统中安全执行复杂算法。最终方案确立时间锚定与变步长补偿混合架构。

    背景与目标

    平台定位

    H7_BSP 是一个面向机器人电控的通用板级支持包，承载视觉通信、多电机控制、IMU 姿态解算等高阶应用。它并非针对某一台具体机器人的专用固件，而是一个可复用的基础平台——各业务（底盘、云台、发射）从 main 分支拉取独立分支迭代。

    核心矛盾

    在引入 FreeRTOS 的嵌入式平台上，存在两种对立的工程路线：

    路线 策略 优势 致命缺陷
    纯 RTOS 路线 所有逻辑（含姿态解算和 PID）放在 RTOS 任务中，以 osDelayUntil 维持周期 代码组织清晰，资源调度灵活 osDelayUntil 的唤醒抖动会毁掉积分和微分项精度
    纯裸机中断路线 开启多个硬件定时器直接跑 PID 和滤波 时间精度极高 在 RTOS 环境中极易触发优先级踩踏、总线争抢和 HardFault

    H7_BSP 的架构目标：在保留 RTOS 灵活调度能力的同时，获得裸机中断级别的时间精度。

    核心方案：时间锚定与变步长补偿

    设计思路

    整体架构分为三个层次：

    • 时间锚点层 — 纯硬件计时器（TIM5），提供全局微秒级时间基准
    • 特权采集层 — 高优先级硬件中断（0~4），只做数据采集和时间戳记录
    • RTOS 解算层 — FreeRTOS 任务（5~14），执行复杂的滤波和控制算法

    时间锚点：全局原子钟

    配置 TIM5 作为全系统时间基准：

    • 计数模式：向上自由计数，微秒级精度
    • 中断配置：不触发任何中断，仅供其他模块读取当前计数值
    • 设计原则：纯粹的"原子钟"，只负责计时，不参与任何调度
    static inline uint32_t BSP_GetMicroseconds(void) {
    return __HAL_TIM_GET_COUNTER(&htim5);
}

    详见 时间戳系统。

    特权采集层：硬件中断（优先级 0~4）

    此层运行在 FreeRTOS 临界区之上，拥有最高执行权限。

    职责：

    • 在 IMU 数据就绪时立即读取时间锚点的精确时间戳
    • 通过 SPI DMA 发起传感器数据读取
    • 读完后发送任务通知唤醒解算任务

    红线约束：

    • 禁止执行任何浮点运算或矩阵操作
    • 禁止调用任何 FreeRTOS API（包括 FromISR 后缀函数）
    • 中断服务函数执行时间必须控制在微秒级

    RTOS 解算层：FreeRTOS 任务（优先级 5~14）

    所有计算密集型工作在此层完成，包括 Kalman 滤波、PID 控制、运动学解算等。

    关键机制 — 变步长补偿：解算任务不使用固定 \(dt\) 常量，而是通过时间锚点计算真实的时间增量，消除 RTOS 调度抖动对算法的破坏。

    为什么固定 \(dt\) 是危险的：

    • 积分项：抖动导致积分累加速率不均匀，Kalman 滤波状态估计漂移
    • 微分项：相邻两次采样的实际间隔不等，算法假设相等时产生剧烈噪声尖刺
    • 前馈项：基于错误时间增量计算的目标变化率偏离真实值

    具体实现参见 PID 控制器 的 Class_PID::TIM_Calculate_PeriodElapsedCallback。

    中断优先级分层规范

    STM32H7 的 NVIC 支持 0~15 优先级（数值越小优先级越高）。FreeRTOS 要求调用其 API 的中断优先级 ≥ configLIBRARY_MAX_SYSCALL_INTERRUPT_PRIORITY（设为 5）。

    高危配置清单

    必须修正的 CubeMX 配置

    以下 DMA 中断优先级必须设置为 5 或更大，否则在中断中调用 osSemaphoreReleaseFromISR() 将触发断言失败或 HardFault：

    • DMA1_Stream5_IRQn（USART1_RX）
    • DMA2_Stream3_IRQn（USART10_RX）
    • MDMA_IRQn（若有调用 RTOS API 需求）

    FDCAN 波特率校验

    FDCAN2 的波特率在 CubeMX UI 中可能显示异常。必须在初始化后通过寄存器回读确认三路 CAN 总线均工作在 1 Mbps。

    Git 协作策略

    采用主干开发 + 项目分支模式：

    • main：维持基础平台稳定，只接受经过验证的平台级特性
    • develop：新特性的集成测试分支
    • project-*：各具体机器人从 main 拉取的独立业务分支
