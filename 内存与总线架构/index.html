    STM32H7 内存与总线架构详解

    文档摘要

    STM32H7 系列拥有嵌入式 MCU 中最复杂的内存架构之一。本文档以 H723/H730 为基准，解析内部总线矩阵、内存区域功能划分，以及 DMA 控制器的访问约束。重点阐明一个关键工程陷阱：DMA 无法访问 TCM 内存，以及如何通过修改链接器脚本来正确规划数据布局。

    总线架构模型

    STM32H7 内部的数据通路可用三级交通网络来理解：

    TCM 总线

    TCM（Tightly-Coupled Memory）是 CPU 核心的专属数据通道。通过它访问 ITCM/DTCM 具有零等待周期、零总线仲裁的特性，是 CPU 性能的极限保障。代价是此通道对其他总线主设备（DMA、MDMA）完全不可见。

    AXI 总线

    AXI（Advanced eXtensible Interface）是贯穿全芯片的高速主干道，支持并行传输和乱序完成。CPU、DMA1、DMA2、MDMA 均可通过 AXI 总线矩阵访问挂载在其上的 SRAM 和外设。

    AHB/APB 总线

    AHB/APB 是连接低速外设（UART、SPI、GPIO、I2C）的辅助总线，通过桥接器与 AXI 主干道相连。

    内存区域详解

    ITCM RAM — 指令紧耦合内存

    属性 值
    起始地址 0x00000000
    典型大小 64 KB
    访问延迟 零等待（CPU 专属）
    DMA 可达 ❌ 不可达

    用途：存放对执行速度要求极高的代码段，如高频中断服务函数、DSP 运算函数。

    放置方法（GCC）：

    __attribute__((section(".itcm_text")))
void IMU_EXTI_Handler(void) {
    // 时间敏感的中断服务代码
}

    DTCM RAM — 数据紧耦合内存

    属性 值
    起始地址 0x20000000
    典型大小 128 KB
    访问延迟 零等待（CPU 专属）
    DMA 可达 ❌ 不可达 — H7 平台最经典的陷阱

    致命陷阱：CubeMX 默认链接器脚本通常将 .data 和 .bss 段分配到 DTCM。这意味着所有 DMA 缓冲区也被放在了 DMA 不可达的区域，导致所有依赖 DMA 的外设静默失效——无报错、无 HardFault，只是数据永远为零。

    AXI SRAM (RAM_D1) — 通用高速存储

    属性 值
    起始地址 0x24000000
    典型大小 320 KB（H723）
    访问延迟 AXI 总线仲裁延迟（通常 1~2 周期）
    DMA 可达 ✅ 完全支持

    用途：所有需要 DMA 参与的数据缓冲区必须放在此区域：

    • FDCAN 接收/发送缓冲区
    • UART DMA 接收 buffer
    • SPI DMA 读写 buffer
    • USB CDC 数据缓冲区
    • 通用全局变量和静态变量

    内存规划总览

    内存区域 起始地址 DMA CubeMX 默认用途 H7_BSP 推荐用途
    ITCM 0x00000000 ❌ 闲置 高频中断代码（可选）
    DTCM 0x20000000 ❌ 堆、栈、全局变量 仅限 RTOS 任务堆栈
    RAM_D1 0x24000000 ✅ 闲置 必须 放置所有全局/静态变量和 DMA 缓冲区

    链接器脚本修正

    问题

    CubeMX 默认生成的链接器脚本将 .data 和 .bss 段分配到 DTCMRAM：

    /* CubeMX 默认（有问题） */
MEMORY
{
    DTCMRAM (xrw) : ORIGIN = 0x20000000, LENGTH = 128K
    RAM_D1  (xrw) : ORIGIN = 0x24000000, LENGTH = 320K
}

SECTIONS
{
    .data : { *(.data .data*) } > DTCMRAM AT> FLASH
    .bss  : { *(.bss .bss*)  } > DTCMRAM
}

    修正方案

    将 .data 和 .bss 的目标内存区域从 DTCMRAM 改为 RAM_D1：

    /* H7_BSP 修正后 */
SECTIONS
{
    .data : { *(.data .data*) } > RAM_D1 AT> FLASH
    .bss  : { *(.bss .bss*)  } > RAM_D1

    .dtcm_bss (NOLOAD) : {
        *(.dtcm_bss)
    } > DTCMRAM
}

    对于需要显式放置到 DTCM 的高频数据（如任务堆栈）：

    __attribute__((section(".dtcm_bss")))
static StackType_t ins_task_stack[512];

    数据布局原则

    graph TD
    Q{"这个数据由谁访问？"}
    Q -- "仅 CPU 高频读写<br/>（任务堆栈、循环变量）" --> DTCM["放入 DTCM<br/>零延迟访问"]
    Q -- "需要 DMA 搬运<br/>（外设缓冲区）" --> RAM_D1["放入 RAM_D1<br/>DMA 可达"]
    Q -- "两者都需要" --> RAM_D1
    Q -- "高频执行的代码" --> ITCM["放入 ITCM<br/>指令零延迟"]

    经验法则

    当不确定一个变量应该放在哪里时，默认放在 RAM_D1。只有在性能分析证明该变量是热点路径瓶颈时，才考虑将其迁移到 DTCM。

    D-Cache 与 DMA 的一致性问题

    STM32H7 的 Cortex-M7 内核启用了 D-Cache。当 CPU 和 DMA 同时访问 RAM_D1 中的同一块数据时，可能出现缓存一致性问题：

    • CPU 写入 → DMA 读取：CPU 的写入可能还停留在 Cache 中，DMA 读到过期数据
    • DMA 写入 → CPU 读取：DMA 写入的新数据被 Cache 中的旧数据遮蔽

    解决方案：

    方案 操作 适用场景
    手动 Cache 维护 SCB_CleanDCache_by_Addr() / SCB_InvalidateDCache_by_Addr() 对性能要求高，手动管理
    MPU 配置 Non-Cacheable 将 DMA 缓冲区所在区域配置为不可缓存 一劳永逸
    使用 DTCM DTCM 不经过 Cache，天然无一致性问题 仅限不需要 DMA 的数据
